## 1. Problem

The node cache serves a model only once some node holds a complete copy. When an instance's pods start together on
nodes that have none, every pod runs the download. A 4-pod instance of a 1.56 TB model pulls 6.2 TB from the
registry, where one pull would do. Measured in November 2026 on a 4-pod GB300 instance, nvsnap build not recorded
([results/NODE-MODEL-CACHE-2026-11.md](../results/NODE-MODEL-CACHE-2026-11.md)): each pod's download init ran 30 to 32 minutes by its start and end times, about
870 MB/s: 4 times the egress, the registry's rate
limits shared 4 ways, and 4 times the chance one pod's download fails.

Only a pod's own download init can download: it holds the tenant's registry credentials, and the agent must not.
So deduplication has to make one pod download and the others copy what it writes.

## 2. Goals

- One registry download per key and cluster at a time, whatever the number of pods or instances.
- A pod that copies instead of downloading becomes ready shortly after the one that downloads, not a whole copy
  later: it streams the files into its own volume as they land.
- Tens of pods per instance: no node sends more than a few copies, whatever the number of pods.
- Every byte a pod gets is checked against the sha256 manifest of the download that produced it, as today.
- Never worse than today, except in one case. If the downloading pod fails near its end, a waiting pod downloads
  late: up to twice the download time in the worst case. Detecting a stall bounds how late.

## 3. Design

### 3.1 Election

Per key, a `coordination.k8s.io` Lease `nvsnap-model-dl-<key>` in the agent's namespace names the pod that downloads:
`holderIdentity` = `<node>/<pod uid>`. Lease duration 30 s, renewed every 5 s.

A node's agent looks at each pending or running wrapped pod on its node whose download init has not finished and
whose key the node does not have. It does so on a node-scoped pod watch, not a poll. Only pods admitted with single
flight count: their init's command has `--plan-wait`. Other pods keep today's behavior, and the agent leaves them
alone.

1. A peer has a complete copy (the sources ConfigMap): fetch it, as today.
2. Otherwise, once the pod's download init is running (not while it waits for an image or an earlier init), take the
   Lease if it is free or expired. Expired is judged as client-go leader election judges it: by when this agent last
   saw `renewTime` change, not by comparing clocks. The pod becomes the holder, and its plan is `download`.
3. Otherwise another pod holds it: this pod streams (3.3), and its plan is `wait`.

The holder's agent keeps the Lease as long as the pod exists, through init restarts: a restarted init continues from
its volume. It releases the Lease only after the final manifest is served and its node is listed as a source. It
releases with a delete preconditioned on the Lease's `resourceVersion`, after checking it still holds it, so a
holder back from a partition cannot delete a successor's Lease. An agent that restarts finds a Lease naming a pod on
its node and renews it, rather than letting it expire into a second download.

A second pod of the same key on the holder's node streams from the holder like any other.

### 3.2 Plans, and the helper

The agent writes each pod's plan into the key's directory, which the init mounts read-only:
`<key>/.plan-<pod uid>`, one line, written to a temporary file and renamed into place.

| Plan | The helper |
|---|---|
| `download` | Runs the download. When it exits 0, the helper writes the tree's fingerprint to the signal volume (below) and does not exit yet: it waits for `<key>/.final-<pod uid>` (3.4), at most `--final-wait` (120 s), then exits as today. |
| `wait` | Waits while `<key>/.streaming-<pod uid>` is fresh: its own stream, so another pod's ending never ends it. When `<key>/.done-<pod uid>` appears, the agent has filled the pod's volume and checked it: the helper exits `seeded`. |
| (none yet) | Waits for a plan for at most `--plan-wait` (60 s), then behaves as without single flight. |

A `wait` plan can change to `download` (the holder failed, 5). The agent first stops writing the pod's volume and
empties it, then writes the plan. The helper downloads into an empty volume.

A helper that gives up on a stream (`--max-wait`, a stale heartbeat, or a `wait` plan that went away) writes
`downloading` to the signal volume, and writes it again on every poll until it lands. It then waits, at most
`--stop-wait` (600 s), for `.streaming-<pod uid>` to go stale. The agent stops that heartbeat only after its last write
has returned. Only then does the helper empty the volume and download. If the heartbeat is still fresh after
`--stop-wait` (a long file still copying), the helper exits with an error and leaves the volume as it is. The init's
restart finds the plan and the volume and looks again.

A helper that gave up waiting for a plan writes `downloading` to the signal volume before its download writes
anything. The agent writes no plan for such a pod, nor for a pod whose volume is not empty, and a stream already
running checks the signal before each pass of writes and stops. A stream may have started after the helper decided
to download, so after writing the signal the helper reads `.streaming-<pod uid>`. If it is fresh and the plan is not
`download`, the helper waits for it to go stale, as above, and empties the volume before it downloads. A takeover
(5) reads the signal after that heartbeat started and before it empties the volume. If the signal is there, the
agent leaves the volume to the helper and releases the Lease. Either the agent sees the signal, or the helper starts
only after the agent's last write or delete. The agent never writes into, or empties, a volume a download writes.

The helper knows its pod's uid from `NVSNAP_POD_UID`, a downward-API env var admission adds last to the wrapped init.
Resolving the key strips exactly that entry, as it strips the wrapper's command and mounts. Admission does not wrap an
init that sets that variable itself.

The helper cannot write the key's directory (read-only), and must not write into the model volume: any file there
changes a directory's times, which are part of the tree. So admission adds a signal volume, an in-memory `emptyDir`
of 1 MiB mounted only into the wrapped init (`--signal`). The helper writes `downloaded` there, holding the tree's
fingerprint, once its download exits 0. The agent reads it from the host, and knows the download is over while the
init is still running. Resolving the key strips that mount as well.

The streaming heartbeat is `.streaming-<pod uid>`, not today's `.incoming`. A helper from before single flight waits on
`.incoming` for at most `--wait` (600 s), and must not be held by a 30-minute stream.

The helper and the flags admission passes it always match: admission mounts the helper from its own bundle version
(`helperVolume`, `internal/webhook/helper.go`). The exception is a webhook with no bundle id, which mounts the legacy
bundle directory. Single flight is off there.

### 3.3 Streaming

A source serves its pod's volume, read-only, under a prefix no cache route uses:

- `GET /v1/model-cache-live/<key>`: the source pod's uid and state (`downloading`, `done`, `failed`). For each entry of
  its volume: path, type, mode, owner, size, mtime, change time, device and inode, and its sha256 once known.
  When `done`, the final manifest (3.4).
- `GET /v1/model-cache-live/<key>/file?path=P`: the file's bytes.

Files are opened only by the no-symlink `openat` walk a harvest uses (`walk.go`), never by resolving a path and then
opening it, so a pod that swaps a directory for a symlink cannot lead the agent out of its volume. Once `done`, only
files the final manifest lists are served, and only while their device, inode and change time are unchanged.

A streaming node's agent writes straight into its own pod's volume (the `emptyDir`, on the host), while the pod's
helper waits. The agent reads pods through a read-only view of the host, so the chart mounts the kubelet pods
directory read-write for this (`agent.nodeModelCache.kubeletPodsDir`). The agent checks at start that it can write
there; if not, single flight stays off, and admission adds no plans. This adds no copy in the cache and no seed on the pod's critical path. The cache gets its copy afterwards
by an ordinary harvest of that volume.

- It polls `live` every 2 s. A file is copied once its size, mtime and change time have not changed for 10 s, and
  its allocated blocks cover its size, and it is copied again whenever they change. The block rule matters: the
  registry's client sizes each file first and fills it in, sparse, so a file that pauses half-filled would otherwise
  look settled and be copied twice (seen on a cluster, a 1.56 TB download, before the rule). It is written to a temporary name and renamed into place, hashed as it is
  written.
- A file that reappears under a new path with the same device and inode (a downloader's temporary name, renamed) is
  renamed locally, not copied again.
- Up to 8 files copy at a time.

**Relay.** Every streaming node is a source as well. A new streaming node picks, among the holder and the nodes
already streaming, the shallowest one with room (at most 3 consumers each), then the one with the fewest. Fewest
alone builds a chain, since a node that just joined feeds none; on a cluster that made a 3-hop chain, each hop
adding its lag. Each node then sends at most 3 copies, so 30
pods form a tree 4 levels deep. Each level adds its settle time (about 10 s per file), not a full copy. The choice is
recorded in one Lease annotation, `nvsnap.io/feeds`: a JSON map from each streaming pod's identity (`<node>/<pod uid>`)
to the identity it streams from, updated with the Lease's resourceVersion. A conflict or a failed read is retried,
up to 5 times. The cap is best effort: if the choice still cannot be recorded, the pod streams from the holder
unrecorded, since one more stream costs less than another download. If a node's source fails, it picks another: the
failed one leaves the annotation, so no node picks it again, and a node never picks one that streams from it (a
cycle).

### 3.4 The end of the download

The holder's download has exited 0, and its helper is still running and holding the init open, so nothing else
writes the volume.

1. When the signal appears, the holder's agent scans the volume, in the background so a tick does not wait on it. Nothing else writes it while the init is held, so
   this is the download's tree, and its fingerprint must equal the signal's.
2. It builds the final manifest from the hashes it made as files settled, hashing only the rest. Each hash is reused
   only while the file's device, inode, size, mtime and change time are those it was made for.
3. It serves the manifest in `live` as state `done`, and writes the tree's fingerprint to `<key>/.final-<pod uid>`.
4. The holder's helper compares that fingerprint with its own scan of the volume. It reports a mismatch in its
   termination message, then exits, and its engine starts. A mismatch means something else wrote the volume during
   the hold (a sidecar). The agent then keeps no copy, and counts the mismatch.
5. The agent harvests the volume into its cache as today, lists itself as a source, and releases the Lease only
   once it is listed, so a pod that arrives in between fetches the copy rather than downloading.

Holding the init open closes a race the cache has today: an engine that writes into its volume at once would change
the tree before the agent reads it. Here the manifest is read while the volume is quiet.

A streaming node, when its source is `done`:

1. Copies whatever the final manifest lists with a stat its copy does not have, and removes what it does not list
   (temporary files).
2. Checks every file's sha256 against the final manifest. It compares the hash it made while writing, so nothing is
   read again.
3. Gives every entry its recorded owner, mode and mtime, as a seed does, and writes `<key>/.done-<pod uid>`. The
   helper exits `seeded`.
4. Becomes `done` itself, for the nodes it feeds.

If the holder fails, its streaming nodes keep what they have. Under the next holder, a copy whose hash matches the
new final manifest is kept, and the rest is copied.

### 3.5 Disk

A streaming node writes into its pod's `emptyDir`, as the download would have. It needs no cache reservation while
streaming. The harvest afterwards reserves as today.

## 5. Failure handling

| Failure | Result |
|---|---|
| Holder's init fails and restarts | It keeps the Lease and continues from its volume, as today. Streaming nodes recopy what changes. |
| Holder's pod is deleted, or its agent or node dies | The Lease is released or expires (30 s). The first streaming pod to take it becomes the holder. Its agent stops writing its volume, empties it, and flips its plan to `download`. The others keep their copies and continue from the new holder. |
| Holder makes no progress for 5 min (no entry's size or mtime changes) | Streaming nodes stop their heartbeat, and their helpers download. A downloader that writes nothing into the volume until the end looks like a stall, so this costs it 5 minutes and a second download, as today. Reading the pod's network bytes would tell it apart; that is section 9. |
| Final manifest not ready within 120 s | The holder's helper exits anyway. The agent harvests as today if it can; streaming nodes see `failed` and download. |
| A streamed file fails its hash at the end | It is copied again from the source's final tree. A second mismatch fails the stream, and the pod downloads. |
| A stream does not finish within 5 hours, or starts over 20 times | It stops before the helper's own 6-hour bound, so it never writes into a volume the helper has given up on. The pod downloads. |
| The holder's Lease update conflicts (streaming pods record their sources on it) | The renewal is retried; only another holder ends it. |
| The holder published a copy, and a stream fails | No takeover: a new download would repeat a published copy. The stream copies the published copy from a node the sources ConfigMap lists, through the routes a fetch from a peer uses, and checks every file against that copy's manifest. If no listed node serves it, the pod downloads. |
| A takeover cannot empty the volume, the pod's helper downloads on its own, or the pod left the node before it was promoted | The new holder releases the Lease at once, so another waiting pod can take it without waiting for it to expire. |
| Agent restarts on a streaming node | The heartbeat goes stale, and the helper downloads. Before writing the `download` plan, the agent empties the volume it was writing. The plan is written only after that, so the helper downloads into an empty volume. |
| No plan within 60 s (agent down) | The pod downloads, as without single flight. |
| Lease API unavailable | No election. Each pod downloads, as today. |
| Eviction | A key directory with plan files is never evicted: a waiting init has it mounted. Each tick removes the plans of pods no longer on the node, so a plan left from before an agent restart does not pin its key. |

## 6. Security

- The live routes need the same agent authentication as the cache's peer routes. The cache stays off unless
  `--auth-mode=required`.
- A source serves only the volume of a pod on its node whose key it computed from that pod's spec, never from a
  label. Each live request names the pod it reads (`uid`). A node whose source for the key is another pod's volume
  answers 410, and the reader picks another source, so feed counts and relay depth stay with the pod that sends. A pod cannot have its volume served under another tenant's or another model's key.
- Paths are opened by the `openat` walk with no symlink followed. FIFOs and devices are refused. After `done`, only
  manifest files are served, and only while unchanged.
- A streaming node trusts only the final manifest, and checks every byte against it before writing `.done`.
  Everything it saw while streaming was only a hint of what to copy.
- The agent writes into a pod's volume only while that pod's plan is `wait` and its helper waits. The volume is
  empty when streaming starts (else the pod is downloading, and the agent leaves it alone), and every write goes
  through `openat` beneath the volume.

## 7. Tests

Failing first, each with a mutation check of the line it guards:

- Election: one holder among N agents; takeover after expiry, judged by observed renewals; a preconditioned release
  that does not delete a successor's Lease; no election before the init runs; the Lease kept across an init restart.
- Helper: `download` then a held exit until `.final`, or until `--final-wait`; `wait` then `.done`; `wait` flipped to
  `download` into an empty volume; no plan within the bound; a stale `.streaming`; `.incoming` not holding a
  `wait` past its own rule.
- Key: the key is the same with and without the injected variable on the agent's path, and a user's own variable of
  that name is keyed.
- Streaming: an appending writer, a preallocating writer, a temporary-name-then-rename writer (no second copy), a
  file rewritten after it settled, a file that settles and is then deleted. Each ends with exactly the final
  manifest's bytes, owners and modes.
- Serving: a symlink swapped in for a directory mid-stream is refused; after `done`, a file not in the manifest, or
  changed, is refused.
- Relay: a fourth consumer of a source picks another; a relay's failure moves its consumers.

The cluster check is a 4-pod instance on nodes with no copy, measuring the registry bytes (the inits' logs), each
pod's init time, and the peer rates.

## 8. Rollout

Behind `agent.nodeModelCache.singleFlight` (default off, and only with `nodeModelCache.enabled`). With it off,
admission adds no variable and no flag, and the agent writes no plan. Mixed versions are safe:

- A pod admitted without single flight is left to today's rules by an agent with it.
- A pod admitted with it, on a node whose agent lacks it, gets no plan and downloads after `--plan-wait`.

## 9. Later

- **Reflink.** A harvest and a seed could share blocks with the pod's volume instead of writing them again. This is
  a separate change; it needs `copy_file_range` across mounts and a kernel and filesystem check on each cluster.
- **Progress from the pod's network bytes.** It would tell a slow downloader, or one that writes elsewhere first,
  from a stalled one.
- **Key by content.** A different image, or a recipe change that writes the same files, gets a new key and
  downloads again. The next step is to start a missing key from a cached key with the same tenant and model
  identity, then let the download fetch only what differs. It needs care: a download in a different mode can write
  a different tree for the same model (a metadata-only scale-out writes no weights), so it is a separate design.
