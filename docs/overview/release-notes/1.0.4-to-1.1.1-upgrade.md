# Upgrade from NVCF 1.0.4 to NVCF 1.1.1

<Warning>
This upgrade procedure and its validation are still in progress. Follow
[the 1.1.1 qualification issue](https://github.com/dsx-ai-factory/nvcf/issues/3428)
for the remaining work. Do not treat the publication of NVCF 1.1.1 as a
qualified upgrade path until that issue records it.
</Warning>

This guide describes an upgrade of a running deployment from NVCF 1.0.4 to
NVCF 1.1.1. NVCF 1.1.1 selects Self-Managed 1.1.9 for the control plane,
Compute Plane 1.1.1 for each GPU cluster, and Observability 1.1.0. Read the
whole guide, including [What changes](#what-changes), before planning an upgrade.

This guide is for deployments on NVCF 1.0.4.

## Choose your upgrade path

NVCF 1.0.4 is the upgrade stop for every customer on a 1.0.x release. To reach
NVCF 1.1.1:

| You run | Do this |
| --- | --- |
| NVCF 1.0.1, 1.0.2 or 1.0.3 | Upgrade to NVCF 1.0.4 first with the [1.0.2 to 1.0.4 upgrade](./1.0.2-to-1.0.4-upgrade.md), then use the [1.0.4 to 1.1.1 upgrade](./1.0.4-to-1.1.1-upgrade.md). |
| NVCF 1.0.4 | Use the [1.0.4 to 1.1.1 upgrade](./1.0.4-to-1.1.1-upgrade.md). |
| NVCF 1.1.0 | You have already passed the 1.0.4 stop. Use the [1.1.0 to 1.1.1 upgrade](./1.1.0-to-1.1.1-upgrade.md). |

Do not upgrade from a 1.0.x release other than 1.0.4 straight to 1.1.1, and do
not use the 1.0.1 to 1.1.0 procedure for a 1.0.4 deployment.

| NVCF edition | Self-Managed | Compute Plane | Observability |
| --- | --- | --- | --- |
| 1.0.4 | 1.0.10 | 1.0.5 | 1.0.0 |
| 1.1.1 (target) | 1.1.9 | 1.1.1 | 1.1.0 |

The stack releases this guide covers are:

| Stack | Source | Target | Target tag |
| --- | --- | --- | --- |
| Self-Managed (control plane) | 1.0.10 | 1.1.9 | `deploy/stacks/self-managed/v1.1.9` |
| Compute Plane | 1.0.5 | 1.1.1 | `deploy/stacks/nvcf-compute-plane/v1.1.1` |
| Observability | 1.0.0 | 1.1.0 | `deploy/stacks/observability/v1.1.0` |

## Cross-stack upgrade order

These declarations apply to the supported starting release in this guide:

| Transition | Required peer |
| --- | --- |
| Compute Plane 1.1.1 | Self-Managed 1.1.0 or later, subject to the compatibility and maintenance policy |
| Self-Managed 1.1.9 during the upgrade window | Existing Compute Plane 1.0.5 can remain until its upgrade |

Upgrade the control plane first, then each GPU cluster to Compute Plane 1.1.1.

<Warning>
Do not run a whole-stack `make apply` or `helmfile sync` first. The control
plane has stops that must happen in order: dependencies and migrations, the
OpenBao check, core services, then Cassandra replication for high availability.
Choose the high availability (HA) mode in
[Prepare the HA mode and configuration](#prepare-the-ha-mode-and-configuration)
before you apply anything. The default, `preferred`, needs little preparation;
`enforced` needs the full preparation in that section.
</Warning>

### Control plane: behavior that changes

| Area | What happens on upgrade | What you do |
| --- | --- | --- |
| High availability | `highAvailability.mode` is new and defaults to `preferred`. An environment file that does not set it activates HA: replica-safe services scale to 2, Cassandra, NATS and OpenBao run 3 members, and PodDisruptionBudgets and placement rules apply. | Choose `none`, `preferred` or `enforced` in [Prepare the HA mode and configuration](#prepare-the-ha-mode-and-configuration). |
| Cassandra | The chart adds a config setting (`range_request_timeout: 5000ms`). The pod template changes, so the StatefulSet restarts its pods one at a time. The migrations image moves to `nvcf-cassandra-migrations:0.19.4`, whose new migrations only add schema ([Apply the dependency stage](#apply-the-dependency-stage)). | Plan a short Cassandra interruption if you run a single member. |
| OpenBao | The chart moves to 0.37.1 and the migrations image to 0.23.4. The server image and the JWT plugin lifecycle are unchanged. The StatefulSet uses `OnDelete`, so Helm success does not replace the running pods. | Check whether the pods need replacing in [Check the OpenBao pods](#check-the-openbao-pods). |
| Event Ledger | New release `event-ledger`, on by default (`addons.eventLedger.enabled: true`). It uses the existing `event_ledger` keyspace, and its OpenBao setup runs in the OpenBao migrations job. | Keep it on, or set `addons.eventLedger.enabled: false` before you apply. |
| NATS worker authentication | New `nats.workerAuth` setting. The default, `nkey`, keeps today's behavior. | Nothing, unless you switch to `token`. See "Worker NATS Authentication" in [control-plane operations](../../self-managed/control-plane-operations.md). |
| Admin issuer proxy | Now optional (`adminIssuerProxy.enabled`), still on by default. | Nothing, unless you want to disable it. |
| NVCT remote config | New `nvctApi.remoteConfig`, empty by default. | Nothing. |
| Upgrade receipt | The final stage records the installed stack version in `nvcf-upgrade-receipt`. | Validate package stamps first, then compare the receipt with the selected release. |
| Worker sidecars | API and NVCT remote config pin the ESS agent sidecar image to `ess-agent:1.4.5` and the patched NICLLS worker to `nvcf_worker_niclls:2.118.5`. Running functions keep the images they started with. | If you mirror sidecar images, mirror both. |
| LLM add-on image tags | With `addons.llm.enabled`, the request router and Pylon tag must match, and `addons.llm.requestRouter.image.tag` is required. `base.yaml` sets `0.29.3`. | Keep the default unless you mirror or pin it. |
| LLM routes | `ingress.gatewayApi.routes.llmApiGateway.enabled` and `ingress.gatewayApi.routes.llmInvocation.enabled` turn off an LLM route while the add-on is on. | Nothing, unless callers reach the gateway in-cluster. |
| Account bootstrap | `api.accountBootstrap.enabled` lets an install whose account is provisioned another way turn off the bootstrap hook Job. Unset, nothing changes. | Nothing, unless you provision the account another way. |
| Pod annotations | Operator pod annotations per release, for example `api.podAnnotations`. Unset, nothing is rendered. | Nothing. |
| Worker callback proxy | New, off by default. See [Optional: enable the worker callback proxy](#optional-enable-the-worker-callback-proxy). | Nothing, unless you need it. |

## cert-manager images come from upstream

NVCF 1.0.4 already pulls the cert-manager controller, webhook, cainjector,
acmesolver and startupapicheck images from the cert-manager chart's upstream
repositories (`quay.io/jetstack`), and these images do not inherit
`global.image`. NVCF 1.1.0 had briefly defaulted them to the NVCF registry, and
1.1.1 returns to upstream. Coming from 1.0.4, the images stay the same
(`v1.20.5`).

Keep the `image.repository` settings you already use for a private mirror or an
air-gapped registry. Verify them **before** you apply the dependencies stage;
otherwise the cert-manager pods try to pull from the upstream registry and
fail. The settings are `certManager.image.repository` for the controller and
`certManager.webhook.image.repository`, `certManager.cainjector.image.repository`,
`certManager.acmesolver.image.repository` and `certManager.startupapicheck.image.repository`.
See [upstream cert-manager images](../manifest.md#use-upstream-cert-manager-images).

### Observability

Observability 1.1.0 is optional. Self-Managed 1.1.9 also works with the
Observability 1.0.0 stack you already run, so you can upgrade Self-Managed on
its own and keep Observability at 1.0.0. The 1.1.0 release changes only two
charts and no images. In the default monitors it sets the `job` label on the
worker and DCGM series and adds pod target labels (`function-id`,
`function-version-id` and `nca-id`) to the worker series. The chart notes say
federation clients such as the BYOO collector select series by that job name,
and the autoscaler queries worker metrics by function identity. Upgrade
Observability if you rely on either. Function scaling and federation were not
exercised with Observability 1.0.0. The control-plane apply reads an
Observability package when the observability profile is enabled, so either
1.0.0 or 1.1.0 must be in place before the render
(see [Get the 1.1.9 packages and check artifacts](#get-the-119-packages-and-check-artifacts)).

| Chart | 1.0.0 | 1.1.0 |
| --- | --- | --- |
| `nvcf-default-monitors` | 0.2.0 | 0.3.0 |
| `nvcf-otel-collector` | 0.2.0 | 0.3.0 |

| Behavior | What changes | What to do |
| --- | --- | --- |
| PodMonitor job labels | The worker and DCGM PodMonitors now set the `job` label to `nvcf-worker` and `nvidia-dcgm-exporter`. | If your dashboards or alerts select the old job names for these series, update them. |
| Worker pod labels | The worker monitor also carries the `function-id`, `function-version-id` and `nca-id` pod labels onto its series. | Nothing, unless you limit label cardinality downstream. |

with; the new defaults apply to deployments created or replaced afterwards.

- A single-member OpenBao installation is not covered; see

## Before starting

1. Schedule a maintenance window. You will pause new function invocations and
   task submissions, and a single-member Cassandra restarts once.
1. You need an operator workstation with `kubectl`, `helm` 3.12 or later,
   `helmfile` 1.1.x (not 1.2.x), the `helm-diff` plugin 3.11 or later, `jq`,
   `curl`, Mike Farah's `yq` v4, and `ngc` if you download packages from NGC.
   Helmfile 1.2.0 removed sequential execution, which these stacks need. See
   [required tools](../../self-managed/helmfile-installation.md#required-tools-and-software).
1. Keep your existing control-plane and compute-plane directories, your
   `environments/<environment-name>.yaml`, your
   `secrets/<environment-name>-secrets.yaml`, and the registration file for each
   GPU cluster (`<cluster-name>-register-values.yaml`). The upgrade reuses each
   cluster's registration. Do not run `register-cluster` again.
1. Choose canary workloads: one serving function, one function that reads a
   secret, and one running task. You will test them before and after.
1. If you mirror images and charts to a private registry, mirror the 1.1.9
   artifacts first. [Get the 1.1.9 packages and check artifacts](#get-the-119-packages-and-check-artifacts) checks availability.
1. Check the cert-manager image settings in
   [cert-manager images come from upstream](#cert-manager-images-come-from-upstream)
   if the cluster uses a mirror.

## 1. Set deployment values

### Set up the session

Download this read-only script into one directory. [Check the starting state](#check-the-starting-state) and [Render and review the changes](#render-and-review-the-changes) use it to
stop an upgrade that would move an image to an older version:

<Download src="../../../fern/assets/upgrade-checks/check-upgrade-image-moves.py" filename="check-upgrade-image-moves.py">Image move check</Download>

Use a dedicated shell. Replace every value in angle brackets. Run this block
first, and again after any shell restart.

```bash
bash
set -euo pipefail
umask 077

export WORKDIR="$HOME/nvcf-upgrade-1.1.9"
export UPGRADE_SCRIPTS="/absolute/path/to/downloaded-scripts"
export OLD_CONTROL_STACK="/absolute/path/to/existing/nvcf-self-managed-stack"
export OLD_COMPUTE_STACK="/absolute/path/to/existing/nvcf-compute-plane-stack"
export HELMFILE_ENV="<environment-name>"
export CONTROL_CONTEXT="<control-plane-kube-context>"
export BACKUP_DIR="$WORKDIR/backup"
mkdir -p "$WORKDIR" "$BACKUP_DIR"

# One kubeconfig per cluster, so a stray context switch cannot redirect a command.
export CONTROL_KUBECONFIG="$WORKDIR/control.kubeconfig"
kubectl config view --minify --flatten --raw --context "$CONTROL_CONTEXT" > "$CONTROL_KUBECONFIG"

kc() { kubectl --kubeconfig "$CONTROL_KUBECONFIG" "$@"; }
control_helmfile() {
  (cd "$CONTROL_STACK" && HELMFILE_ENV="$HELMFILE_ENV" \
    helmfile --environment default --kubeconfig "$CONTROL_KUBECONFIG" "$@")
}
wait_workloads() {
  local kubeconfig="$1" namespace="$2" workload strategy
  kubectl --kubeconfig "$kubeconfig" -n "$namespace" get deployments,statefulsets -o name |
    while IFS= read -r workload; do
      strategy=$(kubectl --kubeconfig "$kubeconfig" -n "$namespace" \
        get "$workload" -o jsonpath='{.spec.updateStrategy.type}')
      if [ "$strategy" = "OnDelete" ]; then
        printf '%s uses OnDelete; replace its pods with the procedure in this guide\n' "$workload"
        continue
      fi
      kubectl --kubeconfig "$kubeconfig" -n "$namespace" rollout status "$workload" --timeout=15m
    done
  kubectl --kubeconfig "$kubeconfig" -n "$namespace" get pods
}
declare -f kc control_helmfile wait_workloads > "$WORKDIR/helpers.sh"
declare -p WORKDIR UPGRADE_SCRIPTS OLD_CONTROL_STACK OLD_COMPUTE_STACK HELMFILE_ENV \
  CONTROL_CONTEXT BACKUP_DIR CONTROL_KUBECONFIG > "$WORKDIR/session.sh"

kc config current-context
kc get nodes
```

All nodes must be `Ready`. To resume later, start a new `bash`, run
`set -euo pipefail`, set `WORKDIR` to the directory you used above
(`export WORKDIR="$HOME/nvcf-upgrade-1.1.9"`), then
`source "$WORKDIR/session.sh"` and `source "$WORKDIR/helpers.sh"`. The saved kubeconfig holds credentials, so keep
`$WORKDIR` private.

### Get the 1.1.9 packages and check artifacts

Both exact target packages must be published and available to your customer
account before maintenance. Stop if either download or package-stamp check
fails. The NVCF 1.1.1 manifest selects these three targets together; do not mix them
with other stack versions.

Download the three target packages next to each other, in a new directory, so
the relative paths in the Helmfiles resolve the same way they did for your current release.


If you obtain the packages another way, extract them to these three
directories. If the observability profile is enabled (`observability.profile` is
not `disabled`), the control-plane Helmfile reads
`../../observability/helmfile.d/01-observability.yaml.gotmpl`, which resolves to
`$WORKDIR/observability`. That directory must hold an Observability package,
either 1.1.0 or your existing 1.0.0. To keep 1.0.0, export
`OBSERVABILITY_STACK_VERSION=1.0.0` before running the download block, or copy
your existing 1.0.0 stack to that directory and skip its download. Leaving the stack only in
its original location makes the render fail. With the profile `disabled` the
directory is not read.

Check both new package stamps against the selected versions before maintenance:

```bash
check_selected_stack_versions() {
  local actual
  actual=$(cat "$CONTROL_STACK/VERSION") || return 1
  if [ "$actual" != "$STACK_VERSION" ]; then
    printf 'Self-Managed package must report %s; found %s\n' "$STACK_VERSION" "$actual" >&2
    return 1
  fi
  actual=$(cat "$COMPUTE_STACK/VERSION") || return 1
  if [ "$actual" != "$COMPUTE_STACK_VERSION" ]; then
    printf 'Compute Plane package must report %s; found %s\n' "$COMPUTE_STACK_VERSION" "$actual" >&2
    return 1
  fi
}
check_selected_stack_versions
declare -f check_selected_stack_versions >> "$WORKDIR/helpers.sh"
```

package through the release process; do not edit `VERSION`, replace immutable
artifacts or substitute another stack version.

### Prepare the HA mode and configuration

#### Choose the HA mode

| Mode | Result | Needs |
| --- | --- | --- |
| `none` | Keeps your current footprint: no extra replicas, no new PodDisruptionBudgets. | Nothing. |
| `preferred` (default) | Replica-safe services run 2 replicas. Cassandra, NATS and OpenBao run 3 members with soft anti-affinity and zone spread. Pods still schedule when capacity is short. | At least 3 schedulable nodes. |
| `enforced` | Same sizing with hard placement. Pods stay `Pending` rather than co-locate. | At least 3 nodes, 3 zones with capacity, `topology.kubernetes.io/zone` labels, and a `WaitForFirstConsumer` StorageClass. |

`preferred` is the default and needs only enough schedulable nodes, so the
checks below are enough for it. `enforced` refuses to place a pod when a
requirement is missing, so complete every step under
[Prepare for enforced mode](#prepare-for-enforced-mode) before you apply
anything. If this is a single-node cluster, or you are not ready to add
capacity, choose `none`. You can move to HA later. If your Cassandra runs a
single member, first follow
[Expand a single-member Cassandra first](#expand-a-single-member-cassandra-first).
The full behavior, including zone spread, is in the
[high availability guide](../../self-managed/high-availability.md).

Check what your cluster offers:

```bash
kc get nodes -L topology.kubernetes.io/zone
kc get storageclass
kc get nodes --no-headers | wc -l
```

Replica-safe services roll with `maxUnavailable: 0` and `maxSurge: 1`, so leave
room for one extra pod per service.

#### Prepare for enforced mode

Skip this section for `none` and `preferred`. With `enforced`, pods stay
`Pending` instead of co-locating, and an unmet requirement blocks the stage that
creates them. Complete every step before the first apply, and keep the results in
`$WORKDIR`:

1. **Three nodes with capacity.** Each Cassandra, NATS and OpenBao member
   needs its own node. Check that three nodes are `Ready`, schedulable and not
   tainted against these workloads (`kc get nodes`), and that they have the
   CPU, memory and volume capacity for the extra replicas. Replica-safe services
   also run 2 replicas, so keep room for one extra pod per service during a
   rollout: free CPU and memory on at least one node must equal the largest pod
   request.
2. **Three zones.** The nodes must be spread over three zones, each with
   capacity, and every node must carry the `topology.kubernetes.io/zone` label.
   List the label with the first command above. A node without the label cannot
   take a zone-spread pod.
3. **A `WaitForFirstConsumer` StorageClass.** The StorageClass your Cassandra,
   NATS and OpenBao volumes use must show `WaitForFirstConsumer` as its volume
   binding mode (`kc get storageclass`). With `Immediate` binding, a volume can
   be created in a zone that has no node for its pod, and the pod stays
   `Pending`. Existing volumes keep their zone, so check where each existing
   Cassandra, NATS and OpenBao volume lives, and that the zone has a schedulable
   node:

   ```bash
   kc get pv -o custom-columns=NAME:.metadata.name,CLAIM:.spec.claimRef.name,ZONE:.metadata.labels.topology\.kubernetes\.io/zone
   ```

4. **Single-member Cassandra.** If Cassandra runs one member, complete
   [Expand a single-member Cassandra first](#expand-a-single-member-cassandra-first)
   before the dependency stage. The new members land in other zones, so check
   steps 1 to 3 for them too.
5. **Replica overrides.** Remove replica overrides from the secrets file, as in
   [Check the secrets file for replica overrides](#check-the-secrets-file-for-replica-overrides).
   An override conflicts with the `enforced` sizing and fails the render.
6. **Render first.** After you set the mode, render and review the diff in
   [Render and review the changes](#render-and-review-the-changes). Stop if a
   workload would not fit.

If a pod stays `Pending` after the apply, run `kc describe pod` on it and read
the scheduling events before you change the mode. Moving back to `preferred`
later is an environment change and a re-apply of the affected stage.

#### Back up persistent state

Create restorable backups before you change anything. Follow your storage
provider's procedure for volume snapshots as well; the commands below create
the application-level backups.

```bash
CASSANDRA_REPLICAS=$(kc -n cassandra-system get statefulset cassandra -o jsonpath='{.spec.replicas}')
echo "$CASSANDRA_REPLICAS" > "$BACKUP_DIR/cassandra-replicas"
for ordinal in $(seq 0 $((CASSANDRA_REPLICAS - 1))); do
  pod="cassandra-${ordinal}"
  kc -n cassandra-system exec "$pod" -c cassandra -- nodetool flush
  kc -n cassandra-system exec "$pod" -c cassandra -- nodetool snapshot -t pre-1-1-9
done
```

The Cassandra snapshot stays on each persistent volume. It is not an off-cluster
backup, so also copy or snapshot the volumes.

Record the migration ledger too. Each application keyspace keeps its applied
migration version and dirty flag in a table of the `schema_migrations` keyspace.
The migration jobs read it to apply only the pending migrations, so a member that
cannot see a row makes a job replay a migration that already ran. The block saves
the ledger from the original member now, while that member holds all of it:

```bash
read -rs -p "Cassandra administrator password: " CASSANDRA_PASSWORD
printf '\n'
cql_on() (
  set +x
  printf '%s\n' "$CASSANDRA_PASSWORD" |
    kc -n cassandra-system exec -i "$1" -c cassandra -- sh -ec '
      umask 077
      auth_dir=$(mktemp -d)
      trap '\''rm -rf "$auth_dir"'\'' EXIT
      IFS= read -r password
      printf "[auth_provider]\nmodule = cassandra.auth\nclassname = PlainTextAuthProvider\n" > "$auth_dir/cqlshrc"
      printf "[PlainTextAuthProvider]\nusername = cassandra\npassword = %s\n" "$password" > "$auth_dir/credentials"
      cqlsh --cqlshrc="$auth_dir/cqlshrc" --credentials="$auth_dir/credentials" --no-color -e "$1"
    ' sh "$2"
)
LEDGER_TABLES=$(cql_on cassandra-0 "SELECT table_name FROM system_schema.tables WHERE keyspace_name = 'schema_migrations';" |
  tr -d ' \r' | grep -E '^[a-z][a-z0-9_]*$' | grep -vx table_name)
test -n "$LEDGER_TABLES"
for table in $LEDGER_TABLES; do
  printf '%s: ' "$table"
  cql_on cassandra-0 "SELECT version, dirty FROM schema_migrations.$table;" | tr -d ' \r' | grep -E '^[0-9]+\|'
done > "$BACKUP_DIR/schema-migrations-ledger.txt"
cat "$BACKUP_DIR/schema-migrations-ledger.txt"
unset CASSANDRA_PASSWORD
```

Every line must show a version and a dirty flag of `False`. Resolve a dirty ledger
before you continue, then run this block again so the saved file records the
corrected state. Do not run it again after the expansion: it would overwrite the
saved ledger with what the new members can see.

Take the OpenBao Raft snapshot from the active member. A snapshot taken from
a standby fails with `incomplete snapshot`.

## 3. Drain pending work

Stop new production requests and task submissions at their callers. NATS
request queues use memory storage, and the dependency stage can restart NATS.
Wait for queued work to finish; do not cancel it to get an empty queue.

For every affected function and version, use a key with `queue_details` scope
(`NVCF_API_KEY`). The task command below uses a separate key with `list_tasks`
scope (`NVCF_NVCT_API_KEY`) and your Tasks endpoint (`base_nvct_url` and
`nvct_host` in the CLI configuration). Verify both with the
[CLI authentication settings](../cli.md) before you start:

```bash
"$NVCF_CLI" --config "$NVCF_CLI_CONFIG" function queue status "$FUNCTION_ID" "$VERSION_ID"
"$NVCF_CLI" --config "$NVCF_CLI_CONFIG" task list --status RUNNING
```

Queue sizes must reach zero. Record the identities and results of running
tasks. Then check the control plane's own memory streams on every NATS server,
through the monitoring port 8222:

```bash
NATS_MONITOR_PORT=18223
NATS_PODS=$(kc -n nats-system get pods -o json | jq -r '.items[] |
  select(any(.spec.containers[]; .name == "nats")) | .metadata.name')
test -n "$NATS_PODS"
NATS_DRAIN_DIR="$WORKDIR/nats-drain-$(date -u +%Y%m%dT%H%M%SZ)"
mkdir "$NATS_DRAIN_DIR"
for pod in $NATS_PODS; do
  (
    kc -n nats-system port-forward --address 127.0.0.1 "pod/$pod" "$NATS_MONITOR_PORT:8222" \
      > "$NATS_DRAIN_DIR/$pod.log" 2>&1 &
    forward_pid=$!
    trap 'kill "$forward_pid" 2>/dev/null || true; wait "$forward_pid" 2>/dev/null || true' EXIT
    for attempt in {1..30}; do
      kill -0 "$forward_pid"
      grep -q 'Forwarding from 127.0.0.1:' "$NATS_DRAIN_DIR/$pod.log" && break
      sleep 1
    done
    grep -q 'Forwarding from 127.0.0.1:' "$NATS_DRAIN_DIR/$pod.log"
    curl --fail --silent --show-error --connect-timeout 5 --max-time 30 \
      "http://127.0.0.1:$NATS_MONITOR_PORT/jsz?accounts=true&streams=true&config=true" \
      > "$NATS_DRAIN_DIR/$pod.json"
    jq -e '.account_details | type == "array"' "$NATS_DRAIN_DIR/$pod.json"
    jq -e 'all(.account_details[];
      ((.stream_detail // []) | type == "array") and
      all((.stream_detail // [])[];
        (.config.storage | type == "string") and
        (.state.messages | type == "number")))' "$NATS_DRAIN_DIR/$pod.json"
  )
done
jq -se '[.[] | .account_details[]? | .stream_detail[]? |
  select(.config.storage == "memory") |
  {name: .name, replicas: (.config.num_replicas // 1), messages: .state.messages}] as $s |
  if ($s | length) == 0 then error("No memory streams found; check the NATS monitoring endpoint")
  elif any($s[]; .messages > 0) then error("Memory streams not drained; do not roll NATS")
  else {memory_streams: ($s | length), single_replica: ([$s[] | select(.replicas == 1)] | length)} end' \
  "$NATS_DRAIN_DIR/"*.json
```

Every memory stream must show zero messages. A replicated stream (under
`preferred` or `enforced` HA) survives a single restart, but draining it keeps
the result unambiguous. A failed or slow read, a missing stream or a nonzero
count blocks the upgrade. A server whose accounts hold no streams reports no
stream details, which counts as empty; the final check still requires at least
one memory stream across the servers. Each attempt writes to a new directory, so files from an
earlier attempt cannot satisfy the check. Wait for the work to drain
and repeat; do not discard messages. If your NATS monitoring is configured
differently, use its endpoint and keep the same per-server check.
For retained creation messages or stuck deployments, follow the
[recovery steps](../../self-managed/upgrade-recovery.md#inspect-retained-creation-messages)
before proceeding.

## 4. Apply control-plane stages in order

### Expand a single-member Cassandra first

Do this only if `CASSANDRA_REPLICAS` from [Back up persistent state](#back-up-persistent-state)
is `1` and you chose `preferred` or `enforced`. Skip it if Cassandra already runs
3 members, or if you chose `none`. Run it in the maintenance window, after you
drain pending work: while `system_auth` is being raised and repaired, new logins
can fail.

Do not let the upgrade expand Cassandra from one member to three. The chart
raises the `system_auth` replication factor to the new member count in a hook that
runs after the StatefulSet scales, and it does not repair the data. The new
members then hold none of the existing login data, so administrator and service
logins can fail while every member shows `UN`, and the dependency stage times out.
Expand and repair now, on the release you run today, so the upgrade starts from a
normal three-member cluster.

First, make `cassandra-0` the only seed. Cassandra does not stream the existing
data to a member that lists itself as a seed, so a new member that appears in the
old seed list joins without the data. Set the seed list to the original member
only, for the expansion, so that the new members bootstrap. The upgrade later
restores the chart's default two-seed list. The member turns `Ready` a few seconds
before it accepts CQL connections, so the block also waits for the CQL port. It
stops unless Cassandra is a single member:

```bash
test "$(kubectl --kubeconfig "$CONTROL_KUBECONFIG" -n cassandra-system get statefulset cassandra \
  -o jsonpath='{.spec.replicas}')" = "1" || {
  echo "Expected a single-member Cassandra deployment; stop here."
  exit 1
}

kubectl --kubeconfig "$CONTROL_KUBECONFIG" -n cassandra-system patch statefulset cassandra \
  --type strategic -p '{
    "spec": {
      "template": {
        "spec": {
          "containers": [{
            "name": "cassandra",
            "env": [{
              "name": "CASSANDRA_SEEDS",
              "value": "cassandra-0.cassandra-headless.cassandra-system.svc.cluster.local"
            }]
          }]
        }
      }
    }
  }'

kubectl --kubeconfig "$CONTROL_KUBECONFIG" -n cassandra-system rollout status \
  statefulset/cassandra --timeout=10m

for attempt in $(seq 1 60); do
  if [ "$(kubectl --kubeconfig "$CONTROL_KUBECONFIG" -n cassandra-system exec cassandra-0 -c cassandra -- \
    nodetool statusbinary)" = "running" ]; then break; fi
  sleep 5
done
test "$(kubectl --kubeconfig "$CONTROL_KUBECONFIG" -n cassandra-system exec cassandra-0 -c cassandra -- \
  nodetool statusbinary)" = "running"

kubectl --kubeconfig "$CONTROL_KUBECONFIG" -n cassandra-system exec cassandra-0 -c cassandra -- \
  printenv CASSANDRA_SEEDS

kubectl --kubeconfig "$CONTROL_KUBECONFIG" -n cassandra-system exec cassandra-0 -c cassandra -- \
  nodetool status
```

This restarts the original single member. Before you continue, check four things:
the seed list contains only `cassandra-0`, the member is `UN`, the administrator
and service logins still work, and the migration ledger is unchanged from the copy
that [Back up persistent state](#back-up-persistent-state) saved. The block asks
for the password and defines the helper itself, so it also runs in a new shell:

```bash
read -rs -p "Cassandra administrator password: " CASSANDRA_PASSWORD

  set +x
  printf '%s\n' "$CASSANDRA_PASSWORD" |
    kubectl --kubeconfig "$CONTROL_KUBECONFIG" -n cassandra-system exec -i "$1" -c cassandra -- sh -ec '
```

Place the new members in different zones. A member's volume stays in the zone
where the member first starts, and the placement rules that the upgrade applies
later cannot move it. Under `enforced`, two members in one zone leave a pod
`Pending` during the upgrade. If every schedulable node has a
`topology.kubernetes.io/zone` label, add a zone spread rule to the StatefulSet
before you scale. The rule is hard under `enforced` and soft under `preferred`, so
a zone without capacity never leaves Cassandra `Pending` under `preferred`. This
restarts the single member once, and the upgrade replaces the rule with the
chart's own. If any node has no zone label, skip this rule: a node without the
label cannot take a pod that has it.

### Raise replication for HA

Skip this step if you chose `highAvailability.mode: none`.

After the dependency stage, Cassandra has 3 members, but your application
keyspaces keep the replication factor they were created with, so losing one
Cassandra node can still make data unavailable. Wait until all three Cassandra
pods are Ready, then raise each keyspace to RF=3 and repair, one member at a
time. The loop below alters only the keyspaces your installation has and skips
the rest. It validates the deployed data-center name against the live database
before any ALTER. Credentials travel over stdin into a temporary protected
[cqlsh credentials file](https://cassandra.apache.org/doc/stable/cassandra/managing/tools/cqlsh.html#credentials).
Do not enable shell tracing.

Each `ALTER KEYSPACE` in this loop replaces the whole replication map with the
data center it validates. If your keyspaces also replicate to another data center,
add that entry to every `ALTER`, as described in
[Expand a single-member Cassandra first](#expand-a-single-member-cassandra-first).

```bash
CASSANDRA_DC=$(kc -n cassandra-system get statefulset cassandra -o json |
  jq -er '.spec.template.spec.containers[] | select(.name == "cassandra") |
    .env[] | select(.name == "CASSANDRA_DC") | .value')
case "$CASSANDRA_DC" in
  ''|*[!A-Za-z0-9_-]*) echo "Invalid Cassandra data-center name" >&2; exit 1 ;;
esac
read -rs -p "Cassandra administrator password: " CASSANDRA_PASSWORD
printf '\n'
cql() (
  set +x
  printf '%s\n' "$CASSANDRA_PASSWORD" |
    kc -n cassandra-system exec -i cassandra-0 -c cassandra -- sh -ec '
      umask 077
      auth_dir=$(mktemp -d)
      trap '\''rm -rf "$auth_dir"'\'' EXIT
      IFS= read -r password
      printf "[auth_provider]\nmodule = cassandra.auth\nclassname = PlainTextAuthProvider\n" > "$auth_dir/cqlshrc"
      printf "[PlainTextAuthProvider]\nusername = cassandra\npassword = %s\n" "$password" > "$auth_dir/credentials"
      cqlsh --cqlshrc="$auth_dir/cqlshrc" --credentials="$auth_dir/credentials" --no-color -e "$1"
    ' sh "$1"
)
LIVE_DC=$(cql "SELECT JSON data_center FROM system.local;" |
  sed -n '/^[[:space:]]*{/{s/^[[:space:]]*//;p;}' |
  jq -ers 'if length == 1 then .[0].data_center else error("Missing data-center row") end')
test "$LIVE_DC" = "$CASSANDRA_DC"
cql "SELECT keyspace_name, replication FROM system_schema.keyspaces;"
EXISTING_KEYSPACES=$(cql "SELECT keyspace_name FROM system_schema.keyspaces;" | tr -d ' \r')
for ks in schema_migrations nvcf_api nvct_api ess_api api_keys_api sis_api event_ledger nvcf_autoscaler; do
  if printf '%s\n' "$EXISTING_KEYSPACES" | grep -qx "$ks"; then
    cql "ALTER KEYSPACE $ks WITH replication = {'class': 'NetworkTopologyStrategy', '$CASSANDRA_DC': '3'};"
  else
    echo "skipping $ks: not present in this installation"
  fi
done
for pod in cassandra-0 cassandra-1 cassandra-2; do
  kc -n cassandra-system exec "$pod" -c cassandra -- nodetool repair --full
done
unset CASSANDRA_PASSWORD
```

Until the repairs finish, reads at `LOCAL_ONE` can miss rows that exist only on
the original replica. The application keyspaces must now report RF=3 for the validated data center.

JetStream streams are created with the replication factor current at creation
time. The `icms` streams raise themselves to the configured factor when it
starts. Streams created earlier by `nvcf-api` and `invocation-service` stay at
1 replica until you edit them. List them and check:

```bash
kc -n nats-system exec deploy/nats-box -- nats stream report
```

The `Replicas` column lists each member that holds a copy of the stream. A
highly available stream shows three (`nats-0`, `nats-1`, `nats-2`); a stream
created before HA shows one. Raise each stream that shows one:

```bash
STREAM="<stream-name>"
kc -n nats-system exec deploy/nats-box -- nats stream edit "$STREAM" --replicas=3 --force
kc -n nats-system exec deploy/nats-box -- nats stream info "$STREAM"
```

Replace `<stream-name>` with the name from the report, run both commands for
each such stream, and confirm `nats stream info` shows `Replicas: 3`. Use 3, not
2: a 2-replica stream loses quorum when either member is down. The NATS
commands run in the `nats-box` deployment because the `nats` server container
does not include the CLI.

[high availability guide](../../self-managed/high-availability.md#validation) uses):

```bash
kc get nodes -L topology.kubernetes.io/zone
kc -n cassandra-system get pods -o wide
kc -n nats-system get pods -o wide
kc -n vault-system get pods -o wide
kc -n nvcf get deploy nvcf-api -o wide
kc -n nvcf get deploy invocation-service grpc-proxy-deployment -o wide
kc -n ess get deploy ess-api-deployment -o wide
kc get pdb -A
```

Replica-safe services show 2 replicas, and Cassandra, NATS and OpenBao show 3.
`invocation-service` and `grpc-proxy` stay at 1 replica if you set a fixed
worker callback URL. Do not resume traffic until the checks pass. Repeat the
canary from [Check the starting state](#check-the-starting-state), create and invoke a new function with a secret, and confirm
queues make progress. Existing workers keep the images they started with.

## 6. Upgrade each compute cluster

Do this for every GPU cluster, after the control plane is verified. Use the
cluster's existing registration; the cluster, group and account identity must
not change.

### Set the variables

```bash
export COMPUTE_CONTEXT="<gpu-cluster-kube-context>"
export CLUSTER_NAME="<gpu-cluster-name>"
export NCA_ID="<existing-account-id>"
export REGISTRATION_VALUES_DIR="/secure/path/to/existing-registration"
export COMPUTE_KUBECONFIG="$WORKDIR/compute-$CLUSTER_NAME.kubeconfig"
kubectl config view --minify --flatten --raw --context "$COMPUTE_CONTEXT" > "$COMPUTE_KUBECONFIG"
kg() { kubectl --kubeconfig "$COMPUTE_KUBECONFIG" "$@"; }
record_identity() {
  kg -n nvca-operator get configmap nvcfbackend-self-managed \
    -o jsonpath='{.data.cluster-dto\.yaml}' |
    yq -o=json '{"clusterId": .clusterId, "clusterGroupId": .clusterGroupId,
      "clusterName": .clusterName, "ncaID": .ncaID}' |
    jq -eS 'if all(.[]; type == "string" and length > 0)
      then . else error("Missing cluster identity") end'
}
kg get nodes
record_identity
```

If the cluster name or account ID was unknown, set `CLUSTER_NAME` and `NCA_ID`
from this output before continuing. The registration file must exist and
match that identity; every node and the NVCA backend must be healthy:

```bash
test -s "$REGISTRATION_VALUES_DIR/$CLUSTER_NAME-register-values.yaml"
declare -p COMPUTE_CONTEXT CLUSTER_NAME NCA_ID REGISTRATION_VALUES_DIR COMPUTE_KUBECONFIG >> "$WORKDIR/session.sh"
declare -f kg record_identity >> "$WORKDIR/helpers.sh"
record_identity | tee "$WORKDIR/identity-before-$CLUSTER_NAME.json"
kg -n nvca-operator get nvcfbackends
kg -n nvca-operator get pods
kg -n nvca-system get pods
```

### Carry your settings into the compute package

```bash
# diff exits 1 when the files differ, which is expected; any other status is an error.
diff -u "$OLD_COMPUTE_STACK/environments/base.yaml" \
  "$OLD_COMPUTE_STACK/environments/$HELMFILE_ENV.yaml" \
  > "$WORKDIR/compute-overrides.diff" || [ "$?" -eq 1 ]
cat "$WORKDIR/compute-overrides.diff"
cp "$COMPUTE_STACK/environments/base.yaml" "$COMPUTE_STACK/environments/$HELMFILE_ENV.yaml"
```

Re-apply each `+` line from `compute-overrides.diff` in
`$COMPUTE_STACK/environments/$HELMFILE_ENV.yaml` (registry, image settings,
observability profile and similar). Do not copy old `nvcaVersion`, `imageTag`
or chart pins over the 1.1.1 defaults. Leave `workerCallbackCaPem` empty unless
you serve worker callbacks over TLS with a private CA. If your clusters share
one environment file, do this once.

### Check images, render and review

```bash
make -C "$COMPUTE_STACK" template HELMFILE_ENV="$HELMFILE_ENV" \
  CLUSTER_NAME="$CLUSTER_NAME" NCA_ID="$NCA_ID" \
  REGISTRATION_VALUES_DIR="$REGISTRATION_VALUES_DIR" \
  KUBECONFIG_FILE="$COMPUTE_KUBECONFIG" COMPUTE_KUBE_CONTEXT="$COMPUTE_CONTEXT" \
  OUTPUT_DIR="$WORKDIR/compute-render-$CLUSTER_NAME"
grep -rhoE 'image:[[:space:]]*"?[A-Za-z0-9._/:@-]+' "$WORKDIR/compute-render-$CLUSTER_NAME" \
  | sed -E 's/image:[[:space:]]*"?//' | sort -u
```

Mirror every image the list shows (NVCA 3.18.10, image credential helper
0.11.4 and the collectors 0.160.0-nv-0.4.9 are new defaults) before you apply. Then review the diff:

```bash
(cd "$COMPUTE_STACK" && HELMFILE_ENV="$HELMFILE_ENV" CLUSTER_NAME="$CLUSTER_NAME" \
  NCA_ID="$NCA_ID" OUTPUT_DIR="$WORKDIR/compute-render-$CLUSTER_NAME" \
  helmfile --environment default --kubeconfig "$COMPUTE_KUBECONFIG" \
  --kube-context "$COMPUTE_CONTEXT" diff --suppress-secrets)
```

Expect the `nvca-operator` chart to move from 1.28.0 to 1.37.1 and the NVCA
agent to 3.18.10. Stop if the diff shows the registration or cluster identity
changing, or unexpected deletions.

### Apply

```bash
make -C "$COMPUTE_STACK" apply HELMFILE_ENV="$HELMFILE_ENV" \
  CLUSTER_NAME="$CLUSTER_NAME" NCA_ID="$NCA_ID" \
  REGISTRATION_VALUES_DIR="$REGISTRATION_VALUES_DIR" \
  KUBECONFIG_FILE="$COMPUTE_KUBECONFIG" COMPUTE_KUBE_CONTEXT="$COMPUTE_CONTEXT" \
  OUTPUT_DIR="$WORKDIR/compute-render-$CLUSTER_NAME"
wait_workloads "$COMPUTE_KUBECONFIG" nvca-operator
kg -n nvca-system get pods
kg -n nvca-operator get nvcfbackends
record_identity > "$WORKDIR/identity-after-$CLUSTER_NAME.json"
diff -u "$WORKDIR/identity-before-$CLUSTER_NAME.json" "$WORKDIR/identity-after-$CLUSTER_NAME.json" \
  && echo "cluster identity unchanged"
```

The operator and agent must be ready, the backend must report healthy, and
the identity files must match. If they differ, stop and inspect them before
doing anything else. Do not install a second copy of shared observability
resources on separate compute clusters; keep your existing configuration.

Confirm from the control plane that the cluster is registered and healthy:

```bash
"$NVCF_CLI" --config "$NVCF_CLI_CONFIG" cluster list-registered
```

Existing function and task canaries must still work with their old worker
images. To move a function to the new worker defaults, replace its deployment
through the [deployment API or CLI](../cli.md#deploy-function); updating the
stack defaults alone does not change running workers or explicit per-function
image overrides. Plan for the interruption while a replacement rolls.

Repeat this step for each remaining GPU cluster, with its own `CLUSTER_NAME`,
`NCA_ID`, registration directory and kube context.

## 7. Resume workloads

Reapply the control plane and confirm it is stable:

```bash
make -C "$CONTROL_STACK" apply HELMFILE_ENV="$HELMFILE_ENV" KUBECONFIG_FILE="$CONTROL_KUBECONFIG"
control_helmfile status
set +e
control_helmfile diff --suppress-secrets --detailed-exitcode
DIFF_EXIT=$?
set -e
echo "diff exit code: $DIFF_EXIT"
if [ "$DIFF_EXIT" -ne 0 ]; then
  echo "STOP: the final diff exited $DIFF_EXIT. Inspect it before you resume traffic." >&2
  exit "$DIFF_EXIT"
fi
```

The final diff must report no changes and exit 0. A nonzero exit means there
are pending changes or a command error. Resolve them and rerun this gate
before continuing:

1. Repeat the canary invocations and compare IDs, results and persistent data
   with the values from [Check the starting state](#check-the-starting-state).
1. Create and invoke a new function and a new task with the inputs you normally
   use, including one function that reads a secret.
1. Resume production submissions and watch queue progress and telemetry.

Keep `$WORKDIR`, the diffs, the render directories and your notes with the
installed configuration as the upgrade record.

## Troubleshooting

| Symptom | Likely cause | What to do |
| --- | --- | --- |
| Render fails with `overrides the highAvailability sizing` | The secrets file sets a replica count that conflicts with the HA sizing. | Remove the override, or set `highAvailability.mode: none`. See [Prepare the HA mode and configuration](#prepare-the-ha-mode-and-configuration). |
| `ImagePullBackOff` in a stage | An image is not in your registry or mirror. | Re-run the [Get the 1.1.9 packages and check artifacts](#get-the-119-packages-and-check-artifacts) checks, mirror the missing image, and retry the stage. |
| Pods `Pending` under `enforced` | Fewer than 3 nodes or zones with capacity, or a StorageClass without `WaitForFirstConsumer`. | Add capacity or fix the StorageClass. `preferred` schedules them but does not give zone protection. |
| A migration job failed | A dependency was not ready, or a hook could not reach its service. | Read the job logs (`kc -n <namespace> logs job/<name>`), fix the cause, and rerun the same stage. Do not disable hooks. |
| OpenBao member sealed after replacement | Auto-unseal has not finished. | Wait, then rerun `check_openbao`. If it stays sealed after five minutes, follow the runbook's recovery guidance. |
| Cassandra member not `UN` | The pod is restarting or joining. | Wait for it to become Ready and rerun `nodetool status`; do not continue while any member is down. |
| The image check prints `BACKWARD` | An old image pin survived in your environment file. | Stop. Remove pins you did not set on purpose ([Prepare the HA mode and configuration](#prepare-the-ha-mode-and-configuration)) and render again. |
| A NATS pod is not Ready after [Apply the dependency stage](#apply-the-dependency-stage) | The NATS pods run as a non-root user (uid 1000), or an image could not be pulled. | Read the pod events and logs. Confirm the images pull from your registry or mirror ([Prepare the HA mode and configuration](#prepare-the-ha-mode-and-configuration)) and that the volume is writable by group 1000. |
| A release fails with `context deadline exceeded` or stays `failed` | A rolling update could not start its extra pod, usually for lack of CPU or memory on one node. | Free capacity and rerun the stage. See [A release stays failed after a stalled rollout](#a-release-stays-failed-after-a-stalled-rollout). |
| Compute plane identity changed | The registration file or `NCA_ID` was wrong. | Stop. Restore the original registration file and rerun the diff before applying. |

### A release stays failed after a stalled rollout

A release can fail with `context deadline exceeded` when a rolling update cannot
start its extra pod, usually for lack of CPU or memory on one node. Stop and
free capacity, then rerun the same stage apply. If the release then stays
`failed` in `helm list` because Helmfile sees no diff, record it as deployed
before you continue, with the name of the failed release:

```bash
control_helmfile -f helmfile.d/02-core.yaml.gotmpl --selector name=<release> sync
```

Use the stage file that owns the release. Then confirm that every release is
`deployed` and every workload is ready before the next stage.

## Optional: enable the worker callback proxy

The proxy is off by default, and this upgrade does not turn it on. Enable it
after the upgrade passes if you run the control plane and the compute plane in
different clusters and want more than one replica of the invocation service or
gRPC proxy. Set `workerCallbackProxy.enabled: true` and
`workerCallbackProxy.workerDomain` in your environment file. The proxy needs its
own DNS name, ports and certificate; follow
[Worker callback proxy](../../self-managed/worker-callback-proxy.md), including
[Expose the proxy and its DNS name](../../self-managed/worker-callback-proxy.md#expose-the-proxy-and-its-dns-name).
The stack refuses to render if the proxy is on while a fixed callback URL such
as `global.workerEndpoints.invocationServiceURL` is set. For the replica rules,
see [Multi-cluster installs](../../self-managed/high-availability.md).

## Rollback boundary

If an upgrade fails, stop and use your deployment's reviewed recovery
procedure. Do not apply your old packages unchanged as a blanket rollback.
Helm rollback does not reverse stored data, does not validate a database or
OpenBao downgrade, and does not revert a Cassandra replication factor you
raised. Keep the OpenBao image and both JWT plugins that 1.0.4 installed; do not
return to an older OpenBao image. The Cassandra migrations in 1.1.9 add columns and indexes, and a rollback
does not remove them. Older services have not been tested against that schema. Restore data only through the reviewed procedure for that datastore,
using the backups from [Back up persistent state](#back-up-persistent-state). After any recovery, verify the original cluster
identities, old-image canaries, durable data and availability. Changing which
package you use does not roll back a running deployment.
